# ADR 0002: Chord model v3 — separate harmony, voicing, and rhythm

- Status: Accepted; Stage 1 implemented (`voice/harmony.rs`), Stages 2–3 pending
- Date: 2026-10-26
- Scope: the `pad.progression` catalog, the chord-slot editor and registry
  rows, the shared chord resolver, the song-code payload for chords, chord
  automation, and the shape `Pad`/`Bass`/`Arp`/`Lead`/`Tonal` read a chord
  through.

## Context

The current chord slot fuses four independent ideas into one eight-field
blob (`ChordSlotControls`, `src/fluid/controls.rs`; rows generated by
`chord_slot_rows!` in `src/fluid/registry.rs`):

- **Harmony** — `degree`, `accidental`, `quality`, `extension`, `extension2`,
  `fifth`.
- **Voicing** — `inversion`, `voicing`.
- **Rhythm** — smuggled into `degree` as sentinels (`REST_DEGREE = -9`,
  `TIE_DEGREE = -8`).
- **Bass** — not in the slot at all; each built-in authors raw MIDI in a
  separate `bass: [i32; 8]` table (`src/fluid/voice/pad.rs`).

Consequences that make the system unpleasant to author in:

- You cannot reason about a chord without holding all four axes at once, and
  the rhythm is invisible in the data.
- Editing one slot seeds a full per-progression override (`edit_chord_slot`,
  `chord_overrides`), so "try a chord here" is entangled with "save an
  override".
- There is no copy/paste. Placing one good chord across a phrase means
  re-entering eight fields per slot — a chore, not a performance.
- The common-tone guardrail
  (`voice_led_progressions_hold_a_tone_through_every_window`) is a global law
  keyed off `song_value >= 9`, not a property of the music. It exists only
  because the pad's 8 s release (default `pad.release_time`) overlaps chords.
  It blocks any chromatic progression (Creep's G–B–C–Cm fails on B→C).
- `pad.evolve_rate` mutates only `degree` (`PadEngine::evolve_progression`),
  so evolve cannot touch colour or voicing.
- The chord editor is a drill into per-field rows (`ChordDrill::Slot`), which
  is a configuration surface, not a musical one.

The chord *content* (the 38 built-in progressions) and the *engine* (voices,
cursor, followers, resolver) are good. What is wrong is the authoring data
model. This ADR replaces the data model and keeps the engine and content.

## Decision

A chord is four separate pieces of simple, typed data, and the progression is
a lane of cells that holds them. Illustrative shapes:

```text
Harmony  { root: HomeDegree, accidental: i8, quality: Quality, tensions: [Tension] }
Voicing  { tones: [Voice] }              // up to 5
Voice    { degree: ChordDegree, octave: i8 }   // ChordDegree names an available tone
Cell     = Rest | Slur | Sound { harmony: Harmony, voicing: Voicing, gate: Gate }
Progression { song_value, name, home_mode, bass: [BassStep], cells: [Cell; N] }
```

1. **Harmony is symbolic and relative to the progression's `home_mode`.** Root
   is a home-mode degree plus accidental; `Quality` is an enum
   (Major/Minor/Dim/Aug/Sus2/Sus4/Power); `Tension` is 7/maj7/9/11/13/6 plus
   the altered set. This is the only part that must stay in key.

2. **Voicing is a small, editable tone array.** Each voice names an available
   chord degree and an octave. The default realizes the close stack. A user
   edits a single tone, omits it, doubles it, or moves its octave — the
   "individual chord tones" capability, as data rather than a preset wheel.

3. **Rhythm is first-class, and it is articulation, not a second
   progression.** A progression is a lane of `Rest` / `Slur` / `Sound` cells.
   The harmony always advances to the step's own chord; the gate only decides
   how it is struck — `Rest` releases the pad, `Slur` voices the chord without
   restarting the attack, `Sound` strikes it. A gate never makes the band
   repeat an earlier chord, so an authored bass line walks every step. The
   sentinel encodings are deleted. The progression editor *is* the sequence
   editor.

4. **Overlap follows the gate, not a global rule.** A `Slur` rides the
   outgoing chord's release; a `Sound` strikes over it; a `Rest` clears the
   pad first. Because the harmony still advances on every gate, a chromatic
   neighbour (Creep's B into C) overlaps unless the lane articulates it, so
   the common-tone test becomes gate-aware and the Creep-style progressions
   become legal by articulation instead of by an exemption.

5. **Bass follows chord roots by default.** An authored bass is a lane of
   scale-degree steps (root, fifth, octave, approach) relative to the
   sounding chord, not a raw MIDI table. Built-in walks are re-authored as
   degree lanes.

6. **Evolve and randomize stay in key and in chord.** Because harmony is
   relative to `home_mode` and voicing may only pick from the chord's
   available tones, generation cannot leave the mode. Evolve gains a
   harmony axis (tensions) and a voicing axis (tone arrangement) in addition
   to the existing degree mutation.

7. **Copy/paste is the placement gesture.** A chord (harmony + voicing) and a
   cell (with its gate) can be copied and pasted onto another step or a
   range. This is required, not optional: without it the rhythmic model is a
   chore and breaks the 15-second onboarding floor.

## Rejected alternatives

- **Add copy/paste to the current eight-field slot.** Leaves the fused axes
  and the sentinels; the reason it is not fun remains.
- **Keep the data, redesign only the UI.** The song code still carries eight
  signed bytes per chord and the rhythm still lives in `degree`; the coupling
  is the problem, not only its presentation.
- **Auto-articulate when adjacent chords share no tone.** Elegant, but it is
  a hidden engine behaviour with unpredictable gating. nooise authors and
  tests its rules; it does not infer them.
- **Unconstrained interval-array voicings.** Simple, but nothing keeps a
  generated voicing in key, which forfeits the evolve/random guarantee.
- **A text chord grammar or DSL.** More expressive than needed and outside
  the small deterministic interaction model in ADR 0001.

## Required invariants

1. Harmony never leaves `home_mode`. Every generated or edited root and every
   tension resolves inside the mode.
2. Voicing never names a tone the chord does not contain. Omission and
   octave moves are free; invention is not.
3. `Rest` and `Slur` are cell variants, not numbers inside a pitch field, and
   neither one holds the harmony back: every cell voices its own chord.
4. Two cells whose releases overlap — adjacent sounding cells with no `Rest`
   between them — share at least one sounding tone. A `Rest` clears the pad,
   so a chromatic neighbour is legal across one. This is the only form of the
   old common-tone rule that survives.
5. The chord a voice sounds is still resolved from one place. `Pad`, `Bass`,
   `Arp`, `Lead`, and `Tonal` continue to read `[i32; 4]` notes, a bass root,
   and a home scale through `ProgressionFollower`/`ProgressionCursor`; the
   follower contract does not change.
6. A chord's displayed name still matches its realized voicing
   (`built_in_chord_names_match_their_voicings` becomes the new-model
   equivalent).
7. Song codes carry chosen musical state only, stay pasteable, and refuse
   retired shapes by name/version (Commandment 4; "retirement, not
   migration").

## Versioning and migration

- **No migration layer.** The chord payload changes shape, so the container
  version moves to 3. A v2 code is refused with `UnsupportedVersion`, exactly
  as v1 is today (`src/fluid/song.rs`). There is no translation path.
- **Built-ins are re-authored through the new encoder**, as `AUTO_STATES`
  already are (`src/fluid/auto.rs`, `just add-morph`). The 38 existing
  progression *contents* are ported: harmony, voicing, rhythm, and bass walk.
- **Range epochs.** Growing or re-meaning the progression dial appends a
  `RANGE_CHANGES` entry (`src/fluid/range_epoch.rs`); the per-field chord
  epoch is retired with the fields. A code that sweeps a moved dial is
  refused (`SongCodeError::StaleRange`).
- **Registry rows** (`pad.chordN_*`, `parse_chord_slot_id`, `CHORD_FIELDS`,
  `CHORD_OVERRIDES_RECORD = 13`) are replaced by the new-model rows. New ids
  append to `SONG_ID_TABLE`; retired ids are removed, not aliased.

## Carried forward

- The 38 authored progression contents (the "bangers"), re-authored.
- `voice/chord.rs` as the harmony resolver: `source_intervals` becomes the
  harmony→available-tones step, and `pad_chord_notes_with_slot` becomes an
  explicit `realize(harmony, voicing)`.
- `MasterKey` and `progression_home` / `HomeMode` — the key and scale model.
- `ProgressionFollower`, `ProgressionCursor`, `ChordWindow`, and the
  `chord_span` telemetry contract.
- The downstream voice path in `bass.rs`, `arp.rs`, `lead.rs`, `tonal.rs`.
- The gate/articulation idea subsumes and retires the Creep problem.
- The song-named progressions (personal build) authored under the new model.

## Consequences

- The Chords page becomes a lane editor with a harmony and voicing
  inspector, plus a clipboard. Progressive disclosure stays: the lane is the
  beginner surface; harmony/voicing/rhythm are the deeper layers.
- `pad.chord_count`, `pad.chord_offset`, `pad.chord_bars`, and
  `pad.chord_notes` are re-expressed as lane length, lane offset, gate units,
  and default voice count; each is a decision in the implementation, not a
  silent reinterpretation.
- Chord automation records are re-keyed; morph's harmony-landing contract is
  preserved at the cell/lane level (`waits_for_harmony`).
- The audio path is the highest-risk area. The lane and resolver must land
  without disturbing `PadEngine`'s layer lifecycle, de-click, or the
  de-clicked automation `AutomationPlan`.

## Verification scenarios

- Every carried-forward built-in reproduces its sounding pitch content, or
  the change is explicitly auditioned and blessed (audio fixture export).
- Gate-aware common-tone: a lane of adjacent sounding cells passes when each
  pair shares a tone; the same chromatic lane passes once a `Rest` sits
  between the colliding pair; a chromatic lane with no `Rest` is refused
  by the test.
- Copy/paste round-trips a chord and a cell/range onto other steps.
- Evolve and randomize never leave `home_mode` over a long seeded run.
- Song-code round-trip covers every new row; a v2 code is refused with
  `UnsupportedVersion`; a moved-dial sweep is refused with `StaleRange`.
- Pad, Bass, Arp, Lead, and Tonal audio and MIDI still agree on the sounding
  chord across progression changes and morph landings.
- Production keyboard replay on both terminal profiles covers the lane
  editor and clipboard.

## Implementation status

Landed:

- `voice/harmony.rs` — `Harmony`, `Quality`, `Voicing`, `realize`, the
  temporary `chord_from_slot` bridge.
- `voice/cell.rs` — `Cell { harmony, voicing, gate }` and `Gate`
  (Rest/Slur/Sound); the resolver and the Pad's sounding test read them.
- `voice/evolve.rs` — the smart one-cell evolution, with engine-level
  guarantees pinned in `tests.rs`.
- Gate semantics — the harmony always advances. `Rest` releases the pad,
  `Slur` voices this step's chord without restarting the swell (via
  `Adsr::start_at` at the level the pad already holds), `Sound` strikes it.
  The old `Tie`/`Hold` and its backwards walk in `ProgressionFollower::follow`
  and `ProgressionCursor::compute_span` are deleted, so an authored bass walk
  plays every step however it is struck.
- Copy/paste — `ChordAction::Copy` keeps the selected step's chord in a
  live-only `EffectExecutor` clipboard; `Paste` writes it onto the selected
  step and `PasteAll` onto every step of the phrase. All three are ordinary
  `/` operations, so the keyboard path is complete and no control was added.
- Stage 2 (rhythm half) — `ChordSlotControls::gate` (`0`/`1`/`2`, Rest /
  Slur / Sound) with the
  `pad.chordN_gate` registry row (`CHORD_FIELDS` nine entries, gate last,
  `reset_at(GATE_SOUND)`); the degree dial narrowed to `-7..=7`;
  `RHYTHM_GATE_EPOCH` appended as a `RangeTarget::ChordSlot` change; record 13
  version 2 (nine bytes, gate last) with version 1 refused; `read_snapshot`
  refuses a stored chord-degree value below the new minimum rather than
  clamping it. All 16 gate ids appended to `SONG_ID_TABLE`.

Remaining (the lane + voicing epic):

- `PadControls.chord_slots` and `chord_overrides` become `[Cell; 16]`;
  `chord_slot` returns an owned `Cell`, so the stored fields *are* `Harmony`,
  `Voicing`, and `Gate` rather than a legacy slot the cell is derived from.
  This cascades through ~50 call sites and ~46 test field reads.
- Voicing becomes explicit: the `voicing` control seeds the four `Voicing`
  voices from a mode and a manual tone edit selects Custom, mirroring how
  `arp.pattern` seeds `arp.step1..16`. Per-tone rows live in a `Voicing ›`
  detail so the step editor keeps its nine rows.
- Naming (`custom_chord_name`, `roman_chord_name`) reads `Cell`/`Harmony`
  instead of `ChordSlotControls`.
- Re-author `AUTO_STATES` through the current encoder (`just add-morph`).
- Retire `legacy_chord_notes` and the `chord_from_slot` bridge.

## Out of scope

- The `nooise make-song` authoring command (a serializer front-end; separate).
- A session/performance document (Commandment 4 keeps it distinct from a
  song code).
- External gear and microphone work.
